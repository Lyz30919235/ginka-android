# PC 视觉小说与资源驱动软件移植为 Android 的提示词

这是可复用的任务模板。填写方括号中的已知信息后，将下方任务正文交给具备文件、终端、GitHub 和 Android 测试能力的 AI。未知项填写“待核实”，不要照搬上一项目的引擎、密码、包名、设备路径或兼容性结论。桌面 TXT 是本文件的交付快照；后续维护以本文件为准。

---

请实际执行下面的移植任务，产出可安装的 Android APK、所需资源、源码和安装说明。不要只推荐工具、罗列方案，或将 EXE 改名为 APK。

## 协作与事实规则

1. 使用简体中文。先确认根目录、适用 AGENTS.md 和已有索引、文档；修改子目录前确认更具体规则。
2. 按当前问题查索引或限定范围搜索，再读标题、符号、命中片段及必要上下文。规则须完整理解；不要因为文件存在就扫描整个项目、日志、依赖和数据目录。
3. 沿用已有同等职责的文件。当前状态、操作方法、配置映射、风险和已确认决定分别维护；每类事实一个权威来源。修改前读取目标段落，定点编辑，不覆盖无关成果。
4. 区分事实、方案、建议、决定与待核实项。缺失事实写“待核实”。区分构建成功、签名通过、安装成功、运行验证、真机验证、用户验收和发布。
5. 对任务已授权的必要步骤持续执行，不反复索要相同许可。仅在缺少关键输入、已有约束冲突或确需新授权时提问；等待期间继续独立工作。文档里的操作步骤不等于执行授权。
6. 保留原始输入与旧交付物。工具、下载、恢复结果、签名密钥和临时目录与源码分开，不记录密码、令牌、Cookie 或个人设备私有路径。

## 第一步：核对输入并识别技术路线

1. 记录文件名、实际长度和 SHA-256；流式检查压缩层、格式签名、索引及必要 CRC。发现多层压缩时逐层识别，不根据扩展名判断完整性。
2. 若需要下载，优先使用服务的可用连接器或可信下载工具，验证完成状态与文件校验；不要导出登录凭据。原始下载失败或只到部分进度时，不把残件当成完整输入。
3. 密码未知时先检查用户已提供的线索，询问必要信息。仅在明确授权及限定预算下做本地归档恢复，命中后独立校验；不要无期限穷举，更不要扩展到账号或无关文件。
4. 先静态查看必要文件结构、脚本、资源头和元数据，识别引擎、脚本 VM、资源格式、插件与原生依赖。不要直接执行来源不明的 Windows EXE、DLL 或安装器。
5. 有源码时评估 Android 交叉编译；有兼容运行时时评估脚本与资源移植；只有 Windows 原生程序且无适配依据时，明确模拟或兼容容器的能力边界。不要假设存在通用 EXE 到 APK 的转换器。

## 第二步：在 GitHub 查找并验证可用项目

1. 按已确认的引擎、脚本、归档和插件类型搜索官方仓库、实现源码与 Release；优先一手文档，不照抄搜索摘要。
2. 仅比较少量匹配候选：支持的格式和接口、Android ABI、最低系统版本、原生插件替代能力、近期维护、许可证、构建方式与现成二进制。
3. 固定选择的 tag、commit、下载资产与 SHA-256。区分某个 tag 中的预编译库和主分支当前源码；使用现成运行时不能宣称重编译了整套引擎。
4. 先记录简短路线：输入格式 → 静态恢复或转换 → 必要兼容层 → Android 运行时 → APK 与资源 → 分层验证。标出已确认能力与待实验问题，再实际执行最小可运行验证。

## 第三步：恢复资源并实现兼容层

1. 在新输出目录执行静态恢复，不覆盖输入。先检查恢复工具是否默认加载原生 DLL；存在这类行为时优先选择纯静态路径。
2. 还原脚本和资源引用时核对目录、大小写、字符编码、哈希算法、扩展名替换、动态拼接和语言后缀。只增加能由明确映射证明的名称别名，不能用随意改名掩盖缺失资源。
3. 对结构化二进制数据，保留字符串、数字、数组、对象、空值与转义等语义；按格式头识别，不只按扩展名选择转换器。不要用空对象或占位数据伪造成功。
4. 顺着实际入口定位初始化顺序、插件加载和接口差异。Windows DLL 不会因为放进资源目录就成为 Android 插件；要找已有原生实现、源码移植或有依据的脚本适配。
5. 修改仅限当前故障所需接口，保持原有剧情与功能。错误提示如“损坏”不自动等于归档损坏；用独立校验、资源存在性、调用栈和当前日志判断。
6. 资源封装后独立校验索引边界、长度、数据校验和及 SHA-256。变更某个资源后定点重建与复核，旧报告不能证明新包正确。

## 第四步：制作 Android 应用

1. 根据运行时证据设置包名、版本、最低 SDK 和目标 SDK。优先支持 arm64-v8a，按运行时实际能力增加 armeabi-v7a；不能仅靠声明 ABI 就声称该架构可运行。
2. 启动器负责首次授权、资源自动发现或目录选择、清晰的缺失文件提示以及启动。资源外置时，交付文件夹层级必须与实际搜索路径一致，并实测没有调试参数的首次启动。
3. 大资源包按约定采用 APK＋资源目录；不要为了宣称单 APK 而塞入不可安装的巨型文件。若用户只接受单 APK 且技术上做不到，说明限制并请求必要选择。
4. 配套配置属于版本的一部分。渲染故障时根据崩溃栈和实际运行试验选择软件、OpenGL 等模式；不能把一个项目的设置当成所有项目的通用修复。
5. 使用独立并妥善保管的签名密钥，校验签名、APK 元数据和各 ABI 的实际库文件。编译用占位类、链接占位库、调试日志和私密签名材料不得进入成品。

## 第五步：按功能验证并修复

1. 使用专用模拟器或已授权设备，输入前确认设备序列号、前台包名和目标应用，避免操作其他实例。
2. 分别检查每个目标 ABI 的安装、冷启动、首次授权、资源发现、标题、语言选择、中文剧情与画面。安装成功或出现标题不算整个移植完成。
3. 测试打开存档界面、创建带有效内容的存档、退出进程后重新启动、读取并继续剧情；验证设置保存。只有用户需要跨架构迁移时再测试对应存档兼容。
4. 按范围检查音频、视频、选择分支和关键界面。音频轨道存在只证明技术层信号，不能替代实际听感；局部剧情通过不能代表全剧情通关。
5. 缺失界面资源时，直接记录逻辑名称、语言变体、最终扩展名和 exists 结果。例如某些 KAGEX 项目会将界面名称动态解析到 file_save_en.pbd；这是排查示例，不能假定所有项目都使用同一命名。
6. 每次修复后重新生成受影响包、部署新文件并复现原失败步骤。仅修改源码、准备别名或打印成功信息，不算部署和运行验证完成。
7. 记录实际测试日期、对象、版本、ABI 与证据入口。模拟器 ARM 转译结果不能替代 ARM 真机；其他系统版本、16 KB 内存页设备及完整流程未测时明确标注。

## 第六步：整理交付与发布

1. 输出 APK、完整所需资源、安装说明、依赖许可、源码或补丁及 SHA256SUMS。完整资源不等于包含测试存档；默认移除测试存档和个人设置，保留必要配置与空目录清单。
2. 安装说明写清手机系统要求、完整资源应放到哪里、APK 安装、首次授权、语言选择、存档备份和常见错误所需证据。逐项与当前启动器和实际目录一致。
3. 创建完整压缩包并测试全部条目的 CRC；核对桌面副本与原件。不要覆盖已有不同内容的同名交付物。
4. 仅在本任务已有明确发布授权时上传 GitHub。确认正确账号、仓库与可见性；未指定可见性时使用私有仓库并告知。源码提交与大型发行附件分开，核对许可证，排除游戏凭据、密钥、缓存、原始下载和无关私人数据。
5. 发布前查当前平台限制。超过单个 Release 资产大小限制时拆分交付，并附经过合并校验的还原脚本、分卷散列与最终文件散列。上传后核实远端 commit、tag、Release 状态、附件名称、长度和可用散列；不能只凭命令退出就说发布完成。
6. 最后更新已有接续文档：当前完成状态、精确版本、证据入口、剩余缺口及下一步。只检查本次改动和直接关联链接，不自动扩大为整个项目审计。

最终请给出可点击的本地交付或 GitHub 链接、简明安装步骤、实际通过的验证、尚未验证的部分，以及新增、修改和沿用的文件摘要。明确本次产物是原生移植、兼容运行时封装还是容器方案，不夸大为通用自动转译。
