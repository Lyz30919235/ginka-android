# 操作手册

## 文档接续

前置条件：已确认项目根目录及适用规则，当前任务已明确。

1. 需要定位时查 [项目索引](../../PROJECT_INDEX.md)，仅选择当前任务相关入口。
2. 接续任务时定位 [当前工作](NOW.md#当前工作)，再按问题读取所需证据；不顺带遍历所有专题。
3. 根据规则写入对应权威来源。修改已有文件前读取目标章节及必要上下文，再定点编辑。
4. 状态有实质变化时修订当前状态；仅将有价值且需追溯的旧过程归档，并更新历史索引。

## 文档检查

前置条件：有本次新增或修改文件的明确清单；检查范围限定为这些文件及其直接关联链接。

1. 确认清单中文件存在且可读；如修改既有文件，对照修改前内容检查是否覆盖无关成果。
2. 核对相对链接是否指向存在的目标，带锚点的链接是否对应目标标题。
3. 检查规则是否齐全、各类事实是否仅有一个权威来源；摘要通过链接引用，不复制专题正文。
4. 核对事实、计划、决定和待核实项的表述；验证结果附日期、对象及范围，不将未执行事项表述为成功。
5. 若任务允许且检查使状态发生实质变化，将证据摘要写入 [NOW.md](NOW.md#核验证据)；交付时说明未执行的验证。

该流程仅检查文档，不触发应用构建、安装、部署或发布。

## 应用操作

候选运行时与游戏专用包的安装、启动记录以 [NOW.md](NOW.md#当前工作) 为准，入口和产物位置见 [MAP.md](MAP.md#移植工作文件)。ADB 操作前确认专用测试实例的序列号与前台包名，避免操作其他应用；安装成功不证明整个游戏流程兼容。

## GINKA 资源与 APK 构建

方法核验日期：2026-10-24；范围为本任务实际执行的静态转换、资源封装、签名及模拟器安装步骤，不构成对其他文件、设备或发布操作的授权。

前置条件：已按授权取得并解包本地输入；保留原始包；固定恢复工具提交并应用 [工具补丁](../../porting/patches/cxdec-ginka.patch)。SDK、JDK、Rust 工具链参数必须指向已定位的安装，不能照抄个人设备路径。

1. 使用已编译的 `cxdec-tools recover xp3hnp <输入目录> <新输出目录>` 静态导出资源。输入目录包括七份 XP3 和原版备份 EXE，仅作为数据读取；不运行输入包中的 EXE 或 DLL。静态探测工具默认派生路径可能加载 DLL，本任务只采用其 `--skip-derive` 探测与 Rust 静态恢复路线。
2. 构建 [PBD 转换器](../../porting/pbd-adapter/Cargo.toml)，执行 `ginka-pbd-adapter <恢复资源目录> <新转换输出目录>`。按格式头识别数据，生成保留类型的 TJS 表达式；输出不可与输入重叠。
3. 执行 [collect_resource_names.py](../../porting/collect_resource_names.py)，通过 `--decompiler` 指向静态工具中的 `tjs2-decompiler`，`--psb-root` 只指定需要解析的场景依赖目录。使用 [restore_aliases.py](../../porting/restore_aliases.py)的 `--hints` 与 PBD 输出恢复明确哈希匹配的名称。动态生成的名称如 `numvalue_10.tft` 可用 `--name` 增补；名称有扩展名替换及语言后缀时也需核对。新增 PBD 名称后再次转换该别名目录，并按需要复核下一轮引用。
4. 使用 [prepare_resources.py](../../porting/prepare_resources.py)组装新源树，`--overlay` 分别传入别名、基础转换和别名转换目录，`--plugins` 指向输入包的插件目录。使用 [build_resources.py](../../porting/build_resources.py)生成新的资源目录；重建单个派生归档时使用 `--archive data.xp3`，由脚本在完整生成与计算散列后替换。保留同目录的渲染配置和 `append/!appendlist.txt`。
5. 使用 [verify_resources.py](../../porting/verify_resources.py)核对当前资源清单、索引边界、文件长度、Adler-32 与 SHA-256；通过 `--report` 保存结果。修改资源后只复核受影响的归档与清单，旧报告不代表新版本。
6. 使用 [build_apk.py](../../porting/build_apk.py)，传入 `--runtime`、`--apktool`、`--sdk`、`--java-home`、`--rust`、`--work`、`--output` 和 `--signing-dir`。工具固定检查运行时散列，编译两个 ARM 目标、附加自有 DEX、对齐并独立签名。签名材料保留在忽略的工作目录；编译声明和链接占位库不进入 APK。
7. 本任务的模拟器安装方式为 `adb -s <专用实例序列号> install --no-incremental --abi <待测ABI> -r <APK>`。将整个资源目录复制到测试设备的 `Download/GINKA/`，再启动 `org.ginka.launcher/.GameActivity`。调试可用 `--es resource_path /sdcard/Download/GINKA/data.xp3` 明确指定资源入口。更换 ABI 后重新安装并复核，不能仅凭 APK 内含库文件报告该架构通过运行验证。

应用首次使用需按提示授予资源访问权限。优先识别 `Download/GINKA/data.xp3` 或内部存储 `GINKA/data.xp3`；也可选择包含该文件的本地目录。不要将运行时渲染配置改回软件模式后沿用 OpenGL 的验证结论。测试阶段的截图、日志与保存目录均只使用本任务创建的独立实例。

## 手机安装与使用

适用：本次 GINKA Android 构建，最低 Android 10，包含 32 位与 64 位 ARM。实际手机兼容性仍需实测；完整验证范围以当前交付说明为准。

1. 解压交付包。将其中整个 `GINKA` 文件夹复制到手机内部存储的 `Download/GINKA/` 或 `GINKA/`，保留七个 XP3、`Kirikiroid2Preference.xml` 和 `append/`，不要只复制 `data.xp3`。手机直接解压时，需同时容纳压缩包与解压后的资源。
2. 安装交付的 `GINKA-0.1.0.apk`，打开 GINKA，按提示授予资源访问权限，然后返回应用。
3. 应用会优先识别上述目录；若提示选择资源，选择直接包含 `data.xp3` 的内层 `GINKA` 文件夹。不要选择包含 APK 的外层交付目录。
4. 首次进入语言设置时，可将界面与正文选择为“中文（简体）”并确认；随后点击标题界面的 `START` 开始。游戏内可用底部保存、读取按钮进入对应页面。
5. 游戏会在资源目录内建立 `savedata/`。迁移资源或更换手机时，一并备份该目录。资源目录中的渲染配置属于配套文件，应与本次资源一起保留。

当前交付不包含模拟器中的测试存档。若出现错误，保留错误页面与资源目录内生成的日志，再核对是否完整复制资源及使用了配套配置。

## GitHub 分卷下载与合并

方法核验日期：2026-10-25；范围：本次完整 ZIP 的二进制分卷、PowerShell 合并及最终 SHA-256，一般手机解压工具的分卷支持未单独验证。

完整 ZIP 超过 GitHub Release 的单附件限制，发行附件采用两卷原始字节分割。版本地址及实际上传状态以 [NOW.md](NOW.md#github-上传)为准。

1. 将 `GINKA-Android-0.1.zip.001`、`GINKA-Android-0.1.zip.002`、`release-parts.json` 和 `merge_package.ps1` 下载到同一文件夹。两卷都需要，单独下载 APK 不包含游戏资源。
2. 在该文件夹打开 PowerShell，执行 `powershell -NoProfile -File .\merge_package.ps1`。脚本源码见 [merge_package.ps1](../../porting/release/merge_package.ps1)。脚本会验证每卷长度和 SHA-256，按清单顺序合并，再验证完整 ZIP；不覆盖内容不同的已有文件。
3. 成功后得到 `GINKA-Android-0.1.zip`，按 [手机安装与使用](#手机安装与使用)解压并复制完整资源目录。保留压缩包或分卷与解压文件时，须为它们同时留出存储空间。

当前原包的分卷清单与合并脚本为发行附件；SHA-256 是完整性校验，不替代来源与许可证核对。仓库和 Release 的实际权限、上传状态及附件结果单独核验，不能把本地合并通过当成上传完成。

## 本地 ZIP 密码恢复

前置条件：用户授权恢复本地归档密码，保持源文件不变；密码、potfile、候选和哈希只放在已忽略的工作目录，不写入项目文档或提交。

核验日期：2026-10-20；仅记录本次实际使用的方法，不授权对其他归档或账号执行恢复。

1. 从 [Hashcat 7.1.2 发行页](https://github.com/hashcat/hashcat/releases/tag/v7.1.2)及 [John v1.9.1-ce 发行页](https://github.com/openwall/john-packages/releases/tag/v1.9.1-ce)取得工具，核对官方资产摘要或校验清单。Hashcat 7z SHA-256 为 `80db0316387794ce9d14ed376da75b8a7742972485b45db790f5f8260307ff98`；John Windows 7z 为 `8259f751378fd0f81a298e52c1277d9c6b08a0d5eb6ba66c46d5dc25b9de3607`。
2. 使用 `zip2john.exe` 提取 PKZIP 验证数据，`hashcat --identify` 识别后，按本包加密条目全部采用 deflate 的证据选择模式 17220。
3. 发行版 `OpenCL/m17220_a3-pure.cl` 的错误 include 会导致编译失败；按[上游已合并修复 #4463](https://github.com/hashcat/hashcat/pull/4463/files)，只将 `inc_checksum_crc32.cl` 引用改为 `inc_checksum_crc.cl`。保留内核自检，不使用 `--force` 或禁用自检选项。
4. 先做有限候选测试，再以掩码 `?d?d?d?d?d?d?d?d` 配合 `--increment --increment-min 1 --increment-max 8` 搜索。实际 OpenCL 使用 `--backend-ignore-hip --backend-ignore-cuda -w 2 --runtime 180`，保留默认温度保护；到时停止，不能把超时表述为穷尽。参数中的工作路径使用项目内实际位置，不把哈希或密码打印到终端。
5. 命中后先用独立 ZIP 实现读取多个条目并校验 CRC，再解包。Bandizip 曾在错误密码与无输入环境下持续提示；本次使用已验证密码、关闭标准输入、日志重定向与 300 秒超时完成解包。不得照抄错误密码测试的交互循环。

实际覆盖、解包和 Android 载入结果以 [NOW.md](NOW.md#密码恢复与资源载入验证) 为准。此次已命中，后续无需重复穷举。

## GeZi 免转存下载

前置条件：用户已授权下载对应文件；工具版本及位置见 [MAP.md](MAP.md#下载工具与文件位置)。本流程是外部下载工具操作，不是项目应用的构建或部署方法。

1. 启动 GeZi；在设置页核对目标保存目录及剩余磁盘空间，避免覆盖已有下载。
2. 在“下载 → 分享链接”填入用户提供的地址并解析；解析出的名称与大小必须与目标相符。
3. 右键目标文件，选择“免转存下载（无法续传）”。该模式中断后可能需要从头下载，不把其他模式的续传能力套用到此模式。
4. 在“任务”页检查实际任务、进度及错误日志；预分配文件的总长度不能证明下载完成。未登录且返回 401 时，由用户本人在“登录”页获取二维码并扫码确认；不读取其他软件的 Cookie，也不导出账号凭证。若已显示登录但旧任务续传返回 401，可重新解析原分享并在独立目录创建新任务；先保留旧文件及元数据，不以取消、删除方式清理残件。
5. 下载完成后同时核对 GeZi 最终状态、预期文件长度及本地 SHA-256。若文件是 LZ4，可用 [MAP.md](MAP.md#下载工具与文件位置) 指定的本地校验依赖流式解码并丢弃输出，检查到达帧末尾、无尾随数据、内置内容校验通过；本地哈希没有来源方原始值对照时只作指纹。该检查不等于内层归档、程序安装或运行验证。

本次执行结果以 [NOW.md：GeZi 验证](NOW.md#gezi-验证) 为准；原有夸克任务保留。
